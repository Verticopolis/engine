The 1994 .TDT save format

What we know about the file, in one place. This page is a knowledge reference: layout, field meanings and how sure we are. The story of how each fact was found lives in the issues and pull requests (Verticopolis/web#1491, Verticopolis/web#1497, Verticopolis/web#740, Verticopolis/web#318, Verticopolis/web#319), not here.

Sources. Tags mark where a fact comes from:

  • [OS]: OpenSkyscraper’s notes (doc/simtower/TDT_format.txt in fabianschuiki/OpenSkyscraper, GPL-3.0).
  • [TD]: the spec in dfloer/tower-docs (tdt_spec.md, CC-BY-SA 4.0; its reference Python reader is AGPL-3.0, so never copy that code into this repo).
  • [RE]: measured by us on game-written saves: the nine 1997 saves in conformance/fixtures/tdt-reddit/ (contributed by u/invokes), saves the retail game wrote under the Wine harness (tools/simtower in Verticopolis/web), and the game’s own re-saves of our exports.

Where the sources disagree this page names the better-evidenced reading.

Who owns what. This page owns meaning: what the values stand for, the unit types, the rules the original follows and what the codec does with them. The byte map, tdt-byte-map.md, owns the layout: every offset, size, field and confidence grade, with an honest unknown for each byte we cannot explain. A table of fields lives there and only there; this page links to it. Change a layout fact in the byte map and a rule here, and keep the two from restating each other.

Clean room. This page restates the layout in our own words; no upstream text or code is copied, and none may be pasted in. Canon may come from observed behavior, published FAQs and reverse-engineered data formats. It must never come from the original games’ source code (including the YootTower archive): nobody working on Verticopolis reads it, even if it is relicensed.

Where it is used. src/tdt/ is the one .TDT codec, held to conformance/tdt-cases.json (see the conformance README). Frontends reach it through the package (loadTdt, adoptTdt, tdtExport) and decode none of the file themselves. In Verticopolis/web the game picks the file, names the download and words the import and export reports. The codec’s own tests are the crate’s tests/tdt_*.rs (import, export, round trips, the real saves, refusals and the fuzzer), which hold it to the facts on this page.

Confidence. High = seen in every real save or in repeated harness runs. Medium = seen in a few saves or one harness run. Low = inferred.

All integers are little-endian. Everything after the floor map is variable-width: walk it, never seek to a fixed offset.

1. File layout

Section titled “1. File layout”
flowchart TB
    H["Header: 560 bytes (0x230)"] --> F["Floor map: 120 floors, each 6 + 18n + 188 bytes"]
    F --> P["People: u32 count N, then N x 16 bytes"]
    P --> R["Retail table: 512 x 18 = 9,216 bytes"]
    R --> E["Elevators: 24 slots, 194 bytes empty, built = 194 + 720 + 324k + 8 x 346"]
    E --> ST["Statistic words: 22 x i32 = 88 bytes"]
    ST --> FIN["Finance: 33 x i32 = 132 bytes"]
    FIN --> UF["Undecoded flags: 12 bytes"]
    UF --> UB["Undecoded bytes: 42 bytes"]
    UB --> PK["Parking: 1,026 bytes"]
    PK --> CL["Medical clinic list: 22 bytes"]
    CL --> S["Stairs: 64 x 10 = 640 bytes"]
    S --> T["Tail: 17,242 bytes in game-written saves (+48 with named units)"]
    T --> V["Our stamp (exports only): VCTDT + u16, 7 bytes"]

The offsets and sizes of every block, with a measured example, are in the byte map, section 1. Everything after the floor map is walked in order, never seeked to.

2. Header

Section titled “2. Header”

The 560-byte header holds the star level (1 to 5, 6 = TOWER), the funds, the time of day and day count, the ground lobby height, the saved viewport and a set of running counts (recycling centers, commercial rooms, security offices, parking stalls, clinics, halls and cinemas, named tenants and people). Field by field, with offsets and grades, see the byte map, section 2.

The floor map starts at byte 560. Our exporter writes the live camera view into the window position when the save has one, else 1105, 3491 (opens on the ground lobby); see view_words_from_view in src/tdt/format.rs.

3. Money scale

Section titled “3. Money scale”

The game shows 100 times the stored value everywhere except the finance window. A stored balance of 20000 shows as $2,000,000. Importers multiply by 100; our engine keeps display dollars and never adopts the x100 storage.

4. Time

Section titled “4. Time”

One day is 2,600 ticks, starting at 7:00 AM. The tick-to-clock mapping is not uniform:

Ticks In-game span Hours Game-seconds per tick
0 to 400 7:00 to 12:00 5 45
400 to 1200 12:00 to 13:00 1 4.5 (lunch crawl)
1200 to 2400 13:00 to 1:00 12 36
2400 to 2600 1:00 to 7:00 6 108 (night sprint)
  • The date changes at tick 2300 (midnight).
  • Calendar: a week is 3 days (2 weekdays, 1 weekend day), a quarter is a week, a year is 4 quarters = 12 days.
  • A clock minute inside the 1880 to 2000 span has no tick of its own; the exporter picks the first tick at or past it, capped at 2599.
  • src/tdt/pacing.rs implements the mapping. The simulation itself runs a uniform 1,440-minute day.

5. Floors

Section titled “5. Floors”

120 slots, index 0 to 119 (ours = tdt - 9):

TDT index Meaning Our floor
0 to 9 B10 to B1 -9 to 0
10 Ground 1
11 to 109 2F to 100F 2 to 100
110 to 119 above the top floor no rooms; the cathedral rises into 110 to 113 (floors 101 to 104)

The cathedral is the one building that stands above floor 100. It is five stacked parts (types 36 to 40) on rows 109 to 113: its bottom part (type 40) sits on floor 100 and the others rise above it, top part (type 36) last. Our Wedding Hall is one unit anchored on floor 100 with the same five stories, so the exporter writes the five parts upward from floor 100 and the importer reads a cathedral by its lowest floor. It is the tallest building the file stores, and the rows above floor 100 hold nothing else.

Lobbies appear at indexes 10, 24, 39, 54, 69, 84, 99 (floors 1, 15, 30, 45, 60, 75, 90).

Each floor is a small header, its unit records and a remap; the fields are in the byte map, section 3.

Logical unit ids. The game numbers a floor’s units and gives a plain floor tile (type 0) no id: the tile’s record carries FF in byte 12 and has no remap entry, and every other record carries its id there. People records, retail rows and the party hall and theatre table name a unit by this id, so it must skip the tiles exactly as the game does. Our exporter numbers the units in record order the same way and writes the remap for the numbered units alone (Verticopolis/web#1932).

Record order matters. Unit records are written in ascending left-edge order with empty-floor (type 0) paving spans interleaved at their real x. The game draws left to right and stops at the first record whose left edge goes backwards, so everything after an out-of-order record renders as sky.

The 18-byte unit record is in the byte map, section 3.1. Multi-story units are stored as one part per floor; importers merge the parts.

5.1 Hotel status (byte 5)

Section titled “5.1 Hotel status (byte 5)”

Bits 3 and 4 hold the room’s stay state, bit 5 the dirty flag, bit 6 the infested flag, bits 0 and 1 the number of guests inside right now.

Status Meaning Confidence
0x08 to 0x0A Checked in (stay state 1); low bits = guests currently inside, 0 to 2 High
0x10 to 0x13 Asleep (stay state 2); low bits = guests inside High
0x18 (24) Clean and vacant; no guests counted. Every room in TOWER1 and MYTOWER, and every TOWER7 room but the 29 dirty ones. Housekeeping also writes it when it cleans a dirty room High
0x20, 0x28, 0x30, 0x38 Dirty, awaiting housekeeping (32, 40, 48 seen in saves; 56 written by the game after it cleared the 0x40 flag); no guests counted High
0x40 Called bug-infested in [TD]. Never found in a save of a tower played in the game. The game keeps it when it loads a file that has it, but clears it from a room that is also vacant or dirty, and no infestation was seen on screen (Verticopolis/web#1629, below) Low

What the original does to these bytes when it saves [RE]. A file we exported was loaded in the retail game and saved again:

  • The “guests inside right now” bits do not survive a load. Rooms we wrote as 0x11 and 0x12 (asleep, one or two guests inside) came back 0x10.

  • Stay state 0 is not a state the game writes. A room we wrote as a bare 0x01 (a rented room, now empty) came back 0x10, so the game read it as a sleeping guest. A clean, vacant room is 0x18.

  • Dirty survives a load but not play. A save made seconds after the load kept every 0x20 room dirty. After about 35 seconds in Fast Mode, housekeeping had cleaned all of them and the game wrote 0x18. A file with dirty rooms therefore reads back dirty only if it is saved again before the cleaners reach them.

  • A room we write as 0x18 can come back 0x20 (dirty) from a save made right after the load. The game does the same to its own file: TOWER1’s 310 rooms, all 0x18 in the game’s save, came back 211 0x20, 91 0x08 and 8 0x09 when it was loaded and saved at once. MYTOWER and TOWER7 kept theirs. So 0x18 is the game’s own byte for a clean vacant room, and what happens to it next depends on the tower and the hour, not on who wrote the file.

  • The 0x40 flag (owner’s PC run, 2026-11-04, three TOWER2 rooms on floor 16). Each status was its own file and its own run. The game loaded 0x40, 0x58 and 0x60 and kept them in a save made at once. Saves made after about a minute of Fast Mode differ by run:

    • 0x58 and 0x60 runs: housekeeping had cleaned the tower’s 96 other dirty rooms to 0x18, and the three flagged rooms had become 0x38, the flag gone and the room still dirty. So the flag cost one more step before a clean room.
    • 0x40 run and the 0x18 control run: housekeeping had not cleaned any room yet, and 0x40 was unchanged.

    No cockroaches or other sign of infestation showed on those rooms on screen. The flag is therefore not our engine’s infested state, which Classic never clears. Our export writes an infested room as dirty (0x20), and the importer reads any room with 0x40 as dirty and counts it in the infested line.

The finance block’s hotel guest lines count exactly the rooms in stay state 1 or 2 at full complement (1 in a single room, 2 in a twin and 2 in a suite), whatever the low bits say. This reproduces the line for every hotel in all nine saves (for example TOWER4: 18 singles, 122 twins and 140 suites, all checked in or asleep, for 18 + 244 + 280 guests). The importer therefore brings every room in stay state 1 or 2 over as a room with its guests, at any hour. Our engine keeps one in-room guest state, so a checked-in guest who was out arrives asleep in the room and checks out at the next morning.

6.1 Metro station, tunnel and parking in the original

Section titled “6.1 Metro station, tunnel and parking in the original”

Measured on TOWER7 in the original game (PC screenshots, release-3.0 tdt-reddit/pc-screenshots) and matching the SimTower wiki. The record-level facts (floor indexes, tile ranges, the paving pieces) are in the byte map, section 3.1. The rules:

  • The metro station is 30 tiles wide and three rows tall (types 31, 32 and 33). The tunnel (type 45) runs along the station’s bottom row only, on both sides of the station, out to the lot’s edges. Nothing else is on that row and nothing can be built below it. B10 is the lowest row, so the ideal spot for the station is B8 to B10.
  • Parking stalls (type 11) are 4 tiles wide and the ramp (type 44) is 16, on floors B1 to B9 (our -8 to 0). The original draws stalls at full size, 4 to 5 per segment between ramps. Short flat-grey paving pieces can sit between stalls and the file still counts those stalls as connected, while stalls a whole paving span (TOWER1: 56 tiles) from their ramp are not. The importer slides stalls that sit less than one stall’s width from their neighbor toward the ramp, so the row chains to it; wider gaps stay split.

Room widths in tiles, from the wiki and the saves: security 16, medical center 26, housekeeping 15, recycling center 25 (two floors), metro 30 (three floors), stairs and escalators 8 (two floors), cinema 31 (two floors), party hall 24 (two floors).

7. People

Section titled “7. People”

The people block is a pool of 16-byte records (layout in the byte map, section 4). Per-tenant populations: condo 3, office 6, fast food 48 (workers plus customers).

The game rebuilds the live crowd on load, so record contents are not needed, but a populated tower must carry a nonzero N or the game faults (“file is already open, or damaged”). An empty tower may carry 0. Our exporter writes the census as zero-filled records. We do not import the roster.

Each unit’s people sit in a row in the block, and its unit record names the first in bytes 8 and 9 (byte map section 3.1): an office keeps 6, a party hall 40 per half and a theatre’s screen piece (types 35 and 34) 56. A party hall must have its people. Without them the game crashes a few seconds after it loads the tower (Verticopolis/web#1932, PC runs headless on 2026-11-12), so after the census our exporter writes each hall half’s 40 people with the floor, the logical unit id, the person number and type 29 (the hall’s upper part, which the game writes for both halves), the rest 0, and points the half’s record at the first. Our exporter writes a theatre the same way the game does (Verticopolis/web#2044): each floor is a 7-tile screen piece (35 below, 34 above) on the left and an auditorium piece (19 and 18) beside it. Both pieces carry the film draw and name the venue’s table row in byte 6, but the table names the screen pieces alone, and only a screen piece owns people: 56, type 18, written like a hall’s. The auditorium’s bytes 8 and 9 stay 0. Our import merges the pieces back into one theatre, joining a screen piece only to the auditorium whose left edge meets the screen’s right edge. Two theaters built flush side by side then stay two: the first one’s auditorium ends where the second one’s screen starts, and a screen never joins the auditorium on its left. All 48 screen pieces in the nine real saves sit on the left of their auditorium.

The pool must keep free records. Our exports before Verticopolis/web#2044 sized N to the records in use, and the game crashed when the player built a theatre in such a tower after loading it (PC run headless, 2026-11-13). The game’s own saves round N up to a multiple of 256 with hundreds spare, so our exporter now rounds the records in use plus 256 up to the next multiple of 256 and pads with zero records.

The zero-filled records are inert (owner’s PC run, 2026-11-04, TOWER4, Verticopolis/web#920 claim 7). With our count (4,173) and with 15,000, the game loaded the tower, ran it with the same population (3,293), kept the pool size in its own save and filled 6 of the records as people appeared. With 0 records it never showed the tower in four tries.

8. Retail table and variants

Section titled “8. Retail table and variants”

The retail table is 512 slots of 18 bytes (byte map section 5). The importer reads four bytes of each filled row: the floor, the logical unit id (mapped to a room through the floor’s remap), byte 8, the visitors the room served yesterday, which seeds its census (section 17), and byte 11, the room’s style.

The game links a room and its row both ways (Verticopolis/web#2044): byte 6 of the room’s unit record is the index of its row, and the row names the room back by floor and logical unit id. This holds for every shop, fast food and restaurant in the seven observation saves (conformance/fixtures/tdt-observed/), and byte 13 of every row is 255. Byte 11 of the row is the style: 0 to 10 for shops and 0 to 3 for fast food and restaurants in those saves, and reading it spreads TOWER7’s shops over all 11 styles where reading byte 6 as the style made 54 of them Men’s Clothing. Our exporter writes rooms and rows the same way. The table holds 512 rows but byte 6 names only 256, so a tower with more retail rooms needs a second byte. Byte 7 is 0 in every retail room of the game’s saves we hold (none has more than 256), so our exporter writes a row past 255 in bytes 6 and 7, low byte first. A headless run of the game on a 280-room export (2026-11-13) confirmed that the game reads it that way: rooms 257 to 280 drew the styles of rows 256 to 279, and the tower ran without a crash. The importer also tries the rows 256 apart, keeping the one that names the room back. A room past the 512th gets no row and opens in the first style, and the export report says so. Our exports before Verticopolis/web#2044 kept the style in byte 6 and wrote rows with unit 0 and no 255, so the importer reads byte 6 as the style when the row it names lacks the 255 or names another room.

The styles, in order:

  • Restaurants (6): English Pub, French, Chinese, Sushi Bar, Steak House.
  • Fast food (12): Japanese Soba, Chinese Cafe, Hamburger Stand, Ice Cream, Coffee Shop.
  • Shops (10): Men’s Clothing, Pet Store, Flower Shop, Book Store, Drug Store, Boutique, Electronics, Bank, Hair Salon, Post Office, Sports Gear.

A headless run on 2026-11-13 settled where the game reads the style (Verticopolis/web#2044): in one of our exports, a Hamburger Stand (byte 11 = 2) and a Sushi Bar (byte 11 = 3) whose byte 6 held rows 5 and 6, both past their style lists, drew as a burger stand and a Japanese restaurant. An earlier Wine render that showed a fast-food unit with byte 6 = 3 as an Ice Cream stand came from a file whose rows did not name their rooms. Shops in a tower with no population draw shuttered (“For RENT”), so their styles show only once they lease.

9. Elevators

Section titled “9. Elevators”

24 slots, one pool shared by standard, service and express shafts.

The slot layout, with its sizes and every field, is in the byte map, section 6. Three facts about how the file is read:

  • The type byte (0 express, 1 standard, 2 service) is authoritative for the kind.
  • An express shaft carries floor entries only for the floors it can stop at: with f = fileIndex - 9, every f from bottom to top where f <= 1 or f is a multiple of 15. That matches all 21 express shafts in the nine real saves, and it includes every basement floor. The serviced bitmap does not size the record.
  • The game keeps all express shafts when the sizes are right (checked on re-saves of TOWER2 and TOWER5, two express each). The table needs no global order: swapping two standard shafts is harmless.
  • Express shafts (Verticopolis/web#740). The exporter writes express shafts after the others. In August 2026 the game lost the shafts behind an express one written early, and later the second of two express shafts written last. The owner’s PC run of 2026-11-04 did not reproduce either loss with today’s encoder: a TOWER2 export holding 24 shafts, two of them express, kept all 24 in the game’s re-save both with the express shafts written last and with them written first. The cause of the August loss was never pinned down, so the express-last order stays. It costs nothing, because the game keeps whatever order it is given.
  • Two shaft records on the same columns load, and the game’s re-save keeps both (the same run, Verticopolis/web#920 claim 1). Neither the original’s build tool nor ours makes such a tower, so a file with them is malformed: the importer keeps the first and drops the later one with a warning, and the export warns about any it writes.
  • The schedule block (the 56 bytes of the Elevator window’s settings; layout in the byte map, section 6.1). Our simulation never reads it. The importer keeps a block that is neither our exporter’s default nor all zero on its shaft as tdtSchedule (112 hex digits), and a save that holds one is version 13, which an older build refuses instead of dropping the block. The exporter writes a kept block back byte for byte and the default otherwise (Verticopolis/web#305, engine 1.59.0).

The stops themselves follow the original’s rule, measured on SimTower 1.0 in the parity run of 2026-11-15 (Verticopolis/web#1527): an express is placed on the ground floor or a 15th floor, its ends can be dragged anywhere, and it stops at the ground floor, every 15th floor (lobby or not) and every basement. An end that is not on one of those floors is not a stop, and its serviced byte is 0. Each allowed stop can be switched off in the game’s Elevator window and the file records it; no other floor can be switched on. The game keeps whatever stops a file gives an express.

The importer keeps the file’s serviced bytes on every express floor, its ends included, and marks the shaft (preserveBasementStops, classicExpressStops) so every load path keeps them. The exporter writes a serviced byte of 0 for an express end the shaft does not stop at, and 1 for the ends of any other shaft. Before Verticopolis/web#1527 the loader kept a lobby-only rule above ground and the importer forced both ends of an express to stop.

Canon car capacities (not read from the file): express 42, standard 21, service 17 (the Windows Help file). The exporter still writes 10 in a service shaft’s header byte, because that byte is unreliable (one PC save showed 21) and the referee pins the bytes. Limits: 24 shafts, 8 cars, spans in src/facilities.rs (POOLED_CAPS, Kind::max_cars, Kind::max_span).

10. Stairs and escalators

Section titled “10. Stairs and escalators”

The stairs table (64 records, fields in the byte map, section 7.7) sits 1,322 bytes after the end of the elevator slots, right after the clinic list, in all nine real saves and in the game’s own re-saves of them. Real saves use types 0 and 1 only. The pool is 64 links shared by stairs and escalators.

  • TOWER6 and TOWER7 fill all 64 slots; the exporter writes slot 0 up and nothing is dropped.
  • Our exports before generation 3 (section 16) wrote this table 160 bytes too early, with a 4-byte gap before it and the flights starting at slot 16. The game read their slot 16 as its slot 0, so flights 49 to 64 landed in its parking list and clinic list and vanished (Verticopolis/web#1501).
  • A stacked column of flights is one single-story record per floor. The exporter writes the same.
  • The importer takes the table at the game’s place when the file is ours from generation 3, or when its clinic list agrees with header byte 52; every other file, including our older exports, is searched for the table by shape (locate_stairs in src/tdt/stair_scan.rs).

11. Statistic words and finance block (88 + 132 bytes)

Section titled “11. Statistic words and finance block (88 + 132 bytes)”

The statistic words and the finance block follow the elevator slots (layout in the byte map, section 7). We write the people lines and their total and leave everything else zero.

The people lines equal what SimTower shows as its live count (TOWER5 and TOWER7 match exactly). Example, TOWER7: 1,428 office, 1,362 shop, 292 fast food, 205 restaurant, 480 theatre, 462 condo. TOWER4 totals 4,515 with 1,620 office and 1,131 condo.

Party halls and theatres count a set audience, observed over a week of play on a tower built for it (Verticopolis/web#1500). A party hall counts 50 from the morning after it opens, every day, whether or not a party was held that day. A theatre counts 40 for each step of its film’s draw plus 40: 120 for a new film (draw 2), 80 at draw 1. The draw is byte 15 of each of the theatre’s records (byte map section 3.1). The census picks up a changed draw the next morning: TOWER7’s theatres fell from draw 2 to 1 on day 18 and its line went from 480 to 320 that morning. Every Reddit save fits this, TOWER4’s mix of draws included (2 x 120 + 2 x 80 = 400). A hall or theatre built that day counts nothing yet (TOWER3).

The draw falls as the film ages (Verticopolis/web#1932). Byte 9 of the theatre’s record in the party hall and theatre table (section 14) counts the mornings its film has shown; it goes up at the morning rollover. Each night the game sets the draw from it: 2 while the count is under 6, 1 from 6 to 8, and 0 from 9 on. So a new film counts 120 for six mornings, 80 for three, then 40 until the film is changed. A tower played on from TOWER7 (its theatres at day 5) fell to 80 per theatre on the expected morning and to 40 three mornings later, and a second run that showed new films reset the count to 0 and the draw to 2. A classic film (the cheaper one) keeps the same clock with its draw held to 1: a run from TOWER7 that set a new film in one theatre and a classic in another on the same morning saw the new film hold 2 for six mornings and the classic 1, and both fall to 0 together. Changing either film sets the count to 0.

The original reads the film table we export (Verticopolis/web#1932, PC parity run of 2026-11-15 on SimTower 1.0). Towers exported with a new film on its first day, a new film on its seventh day and a classic on its second day loaded with those ages: each count went up every morning, the new films drew 2 while the count was under 6, 1 from 6 to 8 and 0 from 9, and the classic held 1 until 9. The theatre line added up to 40 x (draw + 1) for each theatre, as above.

The 12 undecoded flag bytes and the 42 undecoded bytes after the finance block are written as zeros.

12. Parking and the clinic list

Section titled “12. Parking and the clinic list”

Both blocks are laid out in the byte map (parking, clinic list). The parking list holds only the stalls the game counts as connected to a ramp; header byte 50 counts all of them. The list names records of the stall table in the tail (byte map section 8), one per stall holding its floor index and logical unit id, and each stall’s tenant record names its own record in bytes 6 and 7. The game rebuilds the list from that table, so before Verticopolis/web#307 our exports, which wrote the list but left the table empty, lost every stall’s connection a few days after loading. Our exporter now writes the table, points each stall at its record, lists the connected stalls by record, and puts the x of the B1 ramp in header bytes 36 and 37 (FFFF with no ramp), the column the game holds every deeper ramp to. It numbers the clinic ids from 0 up. What makes a stall connected in our engine is in classic-parking-audit.md.

13. Lobby and reachability table [TD]

Section titled “13. Lobby and reachability table [TD]”

A table of 528 six-byte entries (512 per-unit entries plus 16 lobby entries) with a 24-bit elevator bitmask per lobby. Not read or written by us; the 16 lobby records in the tail are described in the byte map, section 8.

14. Tail

Section titled “14. Tail”

The tail follows the stairs table: 17,242 bytes in every real save and in the game’s own re-saves, 17,290 in a tower with named units (layout in the byte map, section 8). In game saves it is mostly zeros with sparse routing state; in the game’s re-save of one of our exports only 48 bytes are non-zero.

The game reads past the stairs table. A file that ends right after the table faults (0x0799). Our exporter writes 25,600 bytes of 0xFF (“all slots empty”) instead, which loads at every star level tried; zeros read as live routing data and invent a phantom population. Matching the exact 17,242 bytes needs a 5-star-and-up load check first. The extent the game reads depends on the file’s own content.

One table in the tail is decoded: the party hall and theatre table at 7,220 bytes past the stairs table, one 12-byte record per hall or theatre (fields in the byte map). The importer reads it when every filled record names two neighboring floors and valid unit ids, and gives each theatre its film’s age from byte 9; otherwise it leaves the table out. Our exporter writes the table inside its 0xFF tail: a record for each finished hall, and for each finished theatre whose film has an age, with the logical ids its index map gives, the audience bytes as the game resets them at night, film 7 for a theatre showing a new film and film 3 for a classic (the engine keeps whether a film is a classic, not its title) and 0 days for a hall. The film number tells the two apart: runs of the original showed the new films The Making of a Star, Love in N.Y., Waikiki Moon and My Man of War, the third to sixth in the game’s list, as 8 to 11, so the seven new films are 6 to 12, and Big Wave, the first classic, as 3. The importer reads a film below 6 as a classic; which numbers the other classics take is not yet observed. The original’s reading of our records has not been checked on a PC yet.

15. Named tenants and people

Section titled “15. Named tenants and people”

16-byte fields holding null-terminated names, at most 15 characters [OS]. The header counts are in section 2. How a name links to a tenant is not known.

16. Our trailer (not part of the 1994 format)

Section titled “16. Our trailer (not part of the 1994 format)”

Our exports end with the ASCII magic VCTDT and a u16 generation (7 bytes). The game never reads it and its re-saves drop it. A reader never requires it.

Generation Express payload sizing
1 By span (the old writer)
2 By eligible floors (section 9)
3 By eligible floors, and the blocks after the elevators and the stairs table where the game keeps them (sections 10 to 12)

An unstamped file, or a generation we do not know, is decided by structural inference (choose_layout in src/tdt/tail.rs): it picks the layout whose walk finds the most shafts; ties go to eligible, serviced, spanned, then serviced-only.

17. What the importer does with it

Section titled “17. What the importer does with it”
  • Treat every count and offset as hostile: size ceilings, caps before loops, typed errors.
  • currentDay is signed; negative values are representable and reset to day 1.
  • Multi-story units arrive as per-floor parts and are merged.
  • Windows byte order only; the Mac version is unknown.
  • Population on load. Offices and condos are seeded from the finance block’s per-class people lines: rooms take people until people / per-room rooms are full (office 6, condo 3), capped by the rooms built, so the app matches the file exactly on the real saves. Hotel guests come from each room’s stay state (section 5.1), which reproduces the finance line for every save. Shops, fast food and restaurants are seeded from each retail row’s byte 8 (yesterday’s served visitors), which is their census in both the original and our engine, so the app matches the file’s three lines on the observation saves (tests/tdt_observed_census.rs). A shop’s and a fast food’s byte 8, and the finance lines that sum them, change together around 10:00 (between the original’s ticks 202 and 247), and a restaurant’s overnight: 23 saves of TOWER5 over four days on the PC parity run of 2026-11-15 (Verticopolis/web#1500). The engine closes their days at those times (MORNING_VENUE_DAY_ENDS_AT_HOUR). A .TDT saved before 10:00 still has that morning’s close to come. TOWER5’s file, saved by its player, counts 80 shop visitors where its rows sum to 40; the parity run’s own saves always added up, so that file’s split is unexplained. Party halls and theatres take the audience section 11 gives them (a theatre’s from its byte 15) when the class adds up to the finance line. A save taken after a film’s draw fell but before the morning census does not add up; when the line splits evenly into an audience each room could count, every room takes that share. Otherwise the class seeds nothing, and each room counts from its first morning in the engine. Each theatre takes its film’s age, and whether it is a classic, from the party hall and theatre table (section 14), so its count falls on the original’s schedule; a file without the table starts every film new.
  • Widths. A room arrives at the width its record gives. New builds of security, medical, housekeeping, recycling and the metro use the sizes in section 6.1, so a rebuilt room matches the original. The engine puts nothing below a metro station and nothing but the station and its tunnel on the bottom basement row.
  • Retail units keep their variant through .vctower and .TDT.

18. Round trip (export then import)

Section titled “18. Round trip (export then import)”

.vctower is lossless; .TDT is lossy. Export then import reaches a fixed point after the first import. Known canonical forms:

  • A plain floor on a sky-lobby story reads back as a lobby (the format has no difference; the game writes type 24 there).
  • A never-simulated shop comes back occupied with a concrete subtype (the format has no vacant retail cell).
  • Yesterday’s venue visitors are not exported: our rows carry the floor alone, so a shop, fast food or restaurant reimports with a census of 0 until its first day passes.
  • A theatre’s film draw and age are exported (Verticopolis/web#1932): byte 15 holds the draw its film had last night and the party hall and theatre table holds the age, so it reimports with the same age. The film itself comes back as film 7, or film 3 for a classic, so a classic stays a classic. A theatre that has not seen a morning in the engine writes no record and reimports with a new film, as it would have shown anyway. Exports before Verticopolis/web#1932 wrote byte 15 as 0, an all-zero index map and no table.
  • Exports before Verticopolis/web#2043 numbered every record, plain floor tiles included, so their venue table named the wrong units, and wrote no people for a party hall, which crashes the original. Re-export the tower to open it there.
  • The paving on a metro station’s bottom row is written as the tunnel (type 45, state 0, no logical id), the way the original writes it beside the station (Verticopolis/web#1503). The importer reads the tunnel as paving, so the tower comes back the same. Exports before Verticopolis/web#1503 wrote plain floor tiles there.
  • A room the file’s flags mark occupied but whose people the finance lines do not count comes back vacant and never lived in.
  • An elevator’s schedule block comes back as it was (tdtSchedule), except that a block equal to our exporter’s default or all zero (a shaft whose cars run in no period) is not kept: it comes back with no tdtSchedule and exports as the default, so the cars of an all-zero shaft run after the trip. Exports before Verticopolis/web#305 wrote the default block for every shaft.
  • An infested hotel room is written as a dirty room (0x20) and comes back dirty. The file’s 0x40 flag is not the same state (section 5.1).
  • A hotel room that was rented and is now empty is written 0x18 and comes back the same. Exports before this fix wrote 0x01 there, which the original reads as a sleeping guest.

Do not teach the importer to reconstruct the pre-canonical state.
