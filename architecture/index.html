Architecture

How the Verticopolis engine is put together: what this repository builds, where the boundary with a host sits, how the simulation steps time, how Classic and Modern differ, how a command and its undo work, what a host reads, how a tower is saved, and how the conformance lock holds every host to the same simulation.

The diagrams are Mermaid; GitHub renders them inline. docs/engine.md maps every module in src/ and covers the tools, the codecs and the WASM build in detail. API.md lists every call a host makes. A frontend’s own architecture (how it draws, takes input and stores files) lives with that frontend: the web game’s is in Verticopolis/web, and the pieces it draws with are in Verticopolis/components.

What this repository builds

Section titled “What this repository builds”

One Rust crate is the whole simulation. Everything else here packages it, checks it or documents it.

flowchart LR
    subgraph repo["Verticopolis/engine"]
        Crate["src/ · Cargo.toml<br/>the verticopolis-engine crate"]
        TS["packages/verticopolis-engine/<br/>TypeScript layer"]
        Conf["conformance/<br/>scenarios · pinned hashes<br/>.TDT cases · save fixtures"]
        Consumer["consumer/<br/>a frontend-free host"]
        Bench["engine-bench/<br/>step-cost bench"]
        Site["docs/engine-site/<br/>the docs site"]
    end

    Crate -->|"cargo publish"| Crates["crates.io<br/>verticopolis-engine"]
    Crate -->|"wasm:build<br/>player + tooling builds"| Pkg["npm<br/>@verticopolis/engine"]
    TS --> Pkg
    Conf --> Pkg
    Conf -. referee .-> Crate
    Consumer -->|"public API only"| Crate
    Bench --> Crate
    Site --> Pages["docs.verticopolis.com"]

    Crates --> Hosts["Rust hosts"]
    Pkg --> JSHosts["JavaScript hosts<br/>(the web game and others)"]
  • The crate (src/, tests/) holds every rule, price, cap, command, save format and gameplay event. Its wasm feature adds the WebAssembly binding; its conformance feature adds the referee and the tools.
  • The npm package carries the player build for the browser (web/) and Node (node/), the tooling build (tooling/, with the test and harness calls), the conformance suite’s files, and the TypeScript layer from packages/verticopolis-engine/.
  • consumer/ depends on the crate by path and uses only the public API. CI builds it in a checkout that holds nothing but the crate, consumer/ and conformance/, with no Node.js.

The boundary: the engine never touches the host

Section titled “The boundary: the engine never touches the host”

The simulation has no access to the DOM, files, the network, the clock, the console, threads or processes. tests/independence.rs fails the build when the library source reaches for any of them or pulls in an unreviewed crate, and tests/read_boundary.rs keeps the tests and binaries reading only the crate and conformance/. A host passes in everything from outside: the elapsed time, the seed, the build name and the time stamp on a save.

A Rust host can skip the binding and call Simulation and the crate’s public modules directly; API.md lists what is stable.

Inside the simulation

Section titled “Inside the simulation”

Simulation (src/sim.rs) owns the tower and its subsystems, each in its own module. State that is never saved (car dispatch, telemetry, housekeeping crews, the weather, the renderer’s effect counters, the memo caches) is rebuilt from the saved state on load.

    Sim --> Clock["Clock<br/>clock.rs: game time, calendar"]
    Sim --> Tower["Tower<br/>tower.rs · tower/<br/>units, transports, the two-layer grid, build caps"]
    Sim --> RNG["Rng<br/>rng.rs: seeded Mulberry32"]
    Sim --> Ledger["Ledger<br/>ledger.rs: income and expense"]
    Sim --> Crowd["Crowd<br/>crowd/: spawning, routing, walking, meals, staff"]
    Sim --> Dispatch["ElevatorDispatch<br/>dispatch*.rs: car routing"]
    Sim --> Econ["economy/ · rent.rs · charges.rs<br/>satisfaction/ · star.rs"]
    Sim --> Events["EventSystem<br/>events*.rs: fires, bombs, treasure, thieves"]
    Sim --> HK["Housekeeping<br/>housekeeping*.rs"]
    Sim --> Services["services.rs<br/>recycling, parking, extermination"]
    Sim --> Mode["GameMode<br/>rules/: rule methods"]
    Sim --> Undo["undo history<br/>undo.rs · undo_journal.rs · sim_undo*.rs"]
    Sim --> Gameplay["gameplay events<br/>gameplay.rs"]

    classDef core fill:#1f6f43,stroke:#0d3,color:#fff;

Determinism is part of the contract. The random numbers come from one seeded generator, maps and sets keep insertion order, and where JavaScript number semantics reach the hash (Math.round, Number#toString) jsmath.rs spells them out. The same seed and the same commands give the same tower on every host, which is what the conformance lock checks.

One step of time

Section titled “One step of time”

A host owes the engine the real time that passed. FrameStepper (src/fixed_step.rs) turns a frame’s milliseconds and the speed into game minutes, carries the remainder to the next frame and caps the carry, so a slow frame never snowballs and a tower comes out the same at any frame rate. Simulation::tick (src/sim_loop.rs) then breaks the minutes into steps of at most 30 that never cross an hour boundary.

flowchart TD
    Advance["advance(owed, ms, minutes per second)<br/>fixed_step.rs: FrameStepper"] --> Tick["Simulation::tick(minutes)<br/>sim_loop.rs"]
    Tick --> Step["advance_step: at most 30 minutes,<br/>never across an hour"]
    Step --> ClockAdv["clock.advance"]
    ClockAdv --> Lock{"bomb search?"}
    Lock -->|no| Move["move people and cars<br/>in 2.5-minute chunks"]
    Lock -->|yes| Build
    Move --> Calls["crowd: hall calls"]
    Calls --> Cars["dispatch: move cars"]
    Cars --> Walk["crowd: walk and ride"]
    Walk --> Staff["housekeeping after each chunk"]
    Staff --> Build["finish construction and searches"]
    Build --> Hour{"new hour?"}
    Hour -->|yes| OnHour["on_hour: presence, checkout, commutes,<br/>schedule retune, crews, satisfaction,<br/>move-ins, star rating"]
    Hour -->|no| Day
    OnHour --> Day{"new day?"}
    Day -->|yes| OnDay["on_day: rent and upkeep by calendar,<br/>random events, VIP, milestones, nudges"]
    Day -->|no| Done["step done"]
    OnDay --> Done

An open undo gesture is paused around every step, so what time does to the tower is never part of an undo step.

Classic vs Modern: the rule-set strategy

Section titled “Classic vs Modern: the rule-set strategy”

A tower is founded under an immutable GameMode (classic or modern). Behavior the two modes disagree on belongs behind the mode’s rule methods (impl GameMode in src/rules/, one file per domain). A subsystem calls self.mode.<x>() instead of testing the mode in its own logic, which keeps mode-specific branches from spreading through the simulation. Classic follows the 1994 game (docs/parity.md is the checklist); Modern may use better algorithms and wider limits.

flowchart TD
    Found["Tower founded with a GameMode"] --> Rules["impl GameMode<br/>src/rules/"]
    Rules --> Subsystems["subsystems call self.mode.x()"]
    Rules --> Catalog["the catalog's rules block<br/>src/catalog.rs · src/catalog/"]
    Catalog --> Frontend["a frontend shows what the engine states"]

The catalog

Section titled “The catalog”

catalog::catalog(mode) (src/catalog.rs) is the reference data every frontend draws a build menu, a price label or a placement ghost from: the world geometry, the economy constants, the pooled caps, and per facility kind its size, cost, star gate, build cap, transport span, cars, rent configuration and more, resolved for one mode so a frontend never applies a rule itself. canBuild answers the price and the refusal of one placement with the same dry run build makes first. conformance/catalog-digests.json pins each mode’s hash, so a changed price or size moves the digest in the pull request that changes it.

Commands and undo

Section titled “Commands and undo”

A host sends a build or an edit as a numeric command. The engine checks it, applies it or refuses it, and answers a result record: done or refused, the money it moved, and the reason for a refusal (lastReason). The host only shows the answer.

Undo and redo live here too. A gesture opens a journal on its first change (src/undo_journal.rs), and the step it commits holds only what that edit changed: the before-image of each unit and shaft it touched and the cash it moved. A step is as big as its edit, whatever the size of the tower. Every completed swap of the tower (a load, a restore, a new founding) drops the steps.

sequenceDiagram
    participant H as Host
    participant E as Engine (binding)
    participant J as undo journal
    participant S as Simulation

    H->>E: undoCapture(label)
    H->>E: buildAt(kind, floor, x)
    E->>S: dry run, then build
    S->>J: record before-images and cash on first change
    S-->>E: done or refused, money moved
    E-->>H: result record (reason through lastReason)
    H->>E: undoCommit()
    E->>J: close the step
    Note over J: a later undo applies the before-images<br/>(sim_undo*.rs)

What a host reads

Section titled “What a host reads”

The engine publishes its state as numbers. viewLayout() describes, once per boot, every slot and width of the frame and the codes it uses. Each frame the host reads a Float64Array of the moving parts (people, cars, effects), and the structure (units and shafts) only when the tower’s revision changes. Panels, reports and the person cards answer numeric records on request. Gameplay events collect in a batch the host drains (drainGameplayEvents), which is where a frontend’s sounds, notices and analytics come from. JSON stays on rare paths: the layout, saves and loads, the catalog and tooling.

flowchart LR
    Sim["Simulation"] --> Frame["frame.rs · view/<br/>frame and structure arrays"]
    Sim --> Panels["panels/ · wasm_port_panels.rs<br/>reports, cards, stats"]
    Sim --> GP["gameplay.rs<br/>event batch"]
    Sim --> Cat["catalog.rs"]

    Frame -->|"Float64Array per frame"| Reader["viewReader / frameReader<br/>(TypeScript layer)"]
    Panels -->|"numeric records"| Host["host UI"]
    GP -->|"drainGameplayEvents()"| Host
    Cat -->|"catalog(mode) JSON"| Host
    Reader --> Host

Saves and files

Section titled “Saves and files”

The engine writes a tower as save text (src/sim_save.rs) and reads it back through its loader (src/load.rs and src/load/), which bounds the inflate, coerces bad values, migrates older saves to the current version (load/migrate*.rs) and refuses a save from a newer build. Saves are untrusted input: the loader skips units of a kind the catalog does not know and clamps car counts and shaft spans, so a hand-edited, corrupt or foreign file loads what it can.

flowchart TD
    Sim["Simulation"] -->|"serialize"| Save["save JSON<br/>sim_save.rs"]
    Save -->|"encode_vctower<br/>fflate.rs deflate + base64"| Vc[".vctower text"]
    Vc -->|"decode_vctower<br/>capped inflate"| Loader["loader<br/>load.rs · load/"]
    Save --> Loader
    Loader -->|"coerce · migrate · refuse newer"| Sim
    TDT[".TDT bytes (1994)"] -->|"import_tdt<br/>src/tdt/"| Save
    Save -->|"export_tdt"| TDTOut[".TDT bytes"]

The .vctower writer produces the same bytes as the web game’s writer for the same save, stamp and time, and the compressor is a line-for-line port of the one the web game uses. The 1994 format is written up in docs/tdt/. A host owns where the bytes go: the engine does no file IO.

The TypeScript layer

Section titled “The TypeScript layer”

packages/verticopolis-engine/src/ ships in the npm package beside the WebAssembly builds, one subpath per module, and imports nothing but the engine.

flowchart TD
    Host["a JavaScript host"] --> HostMod["host/<br/>load and check the package,<br/>boot errors, faults"]
    Host --> Port["port/<br/>EnginePort, commands, queries,<br/>viewReader, frameReader, panels"]
    Host --> Catalog["catalog/<br/>the catalog's types"]
    Host --> Events["events/<br/>the gameplay event catalog"]
    HostMod --> Binding["binding/<br/>the generated Engine declarations,<br/>method lists, catalog reader"]
    Port --> Binding
    Port --> Model["model/<br/>tower and save types"]
    Binding --> Wasm["the WASM Engine"]
    Testing["testing/<br/>mockPort, catalog fixtures"] -.-> Port

EnginePort (port/enginePort.ts) is the one synchronous, numeric interface a JavaScript host holds, and the WASM Engine class implements it directly, with no adapter in between. viewReader decodes the frame arrays into records a renderer draws; it decodes and never decides a rule.

The conformance lock

Section titled “The conformance lock”

Frontends may differ. Simulations may not. The referee replays every scenario in conformance/scenarios/ and must reproduce every pinned checkpoint hash in conformance/expected.json byte for byte. A change to how the game plays regenerates the lock in the same pull request.

flowchart LR
    Scen["conformance/scenarios/"] --> Ref["referee<br/>bin/conformance"]
    Ref -->|"replay commands, tick"| Sim["Simulation"]
    Sim -->|"canonical.rs hash"| Cmp{"matches<br/>expected.json?"}
    Cmp -->|yes| Ok["ok"]
    Cmp -->|no| Diff["first divergent checkpoint,<br/>both hashes (dump to compare)"]
    Ref -.same referee.-> Wasi["built for wasm32-wasip1,<br/>run under Node's WASI in CI"]
    TDTCases["tdt-cases.json"] --> TDTRef["bin/tdt"]
    Digests["catalog-digests.json"] --> CatCheck["crate test + referee"]

The same suite ships in the npm package, so any JavaScript host can prove it runs the real simulation.
